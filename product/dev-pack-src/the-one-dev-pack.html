1Executive Summary

The One (working name) is a purpose-built operations platform that replaces the ClickUp workspace currently running Seamless FM / Byblos Vista / Alpha Fixers — one facilities-maintenance operation trading under multiple brands, with ~98 workspace users and ~21,000 historical work orders. Work orders arrive from client CMMS platforms (Corrigo, Ecotrak, ServiceChannel), email, and the company's own Seamgo tool; they are accepted, dispatched to external subcontractor technicians, quoted, approved by the client, fulfilled, and then paid on both sides — the technician (AP) and the client invoice (AR).

A working prototype exists: a local monorepo app (React + Fastify + embedded Postgres) covering Sprints 1–5 — work-order table and record, 19-status pipeline with phase bar, quote builder with role-gated approval, technician payment requests, an AR audit/invoicing queue, and an obligation ("Pulse") engine — all seeded with real ClickUp data, including hero work order WO-39403.

What this pack is. The repository already contains strong primary documents (process map, roadmap, architecture proposal, sprint spec). What it lacked was the packaged layer a development effort is handed: named personas, written user journeys, a development SOP, a QA/release process, and a consolidated risk register. This document supplies those, and indexes the primary documents rather than duplicating them (§12).

2Product Overview & Principles

The problem

Operations run today on ClickUp plus a constellation of side tools: Yoda (quote builder), PPR (tech payment requests), Argus (AR completion-audit assistant), Quotato (Quo/OpenPhone call & SMS capture with AI quote drafting), an n8n escalation bot watching the contact inbox, and a Teams PDF side-channel for assignments. ClickUp provides primitives (custom fields, statuses, lists, views) but no lifecycle awareness, no money model, no vendor module, and no client-sync boundary. The One rebuilds the primitives ClickUp actually uses — measured from the live workspace: 19 statuses, 102 custom fields, 163 lists — and makes the work-order lifecycle native, so the side tools can be absorbed rather than maintained separately.

Operating rules embedded in the lifecycle

  • Linear with branches, not a loop. Canonical shape is two visits — assess, then fulfil. On-site approval skips the wait; materials is conditional; return trip needed is the exception path.
  • Selective outbound sync. The client's CMMS receives edits, status changes, and curated messages — never the full internal picture. Every update carries an internal-vs-client-facing flag (client_visible).
  • Money flows both ways on the WO. AR bills clients (revenue); AP pays technicians at soft close (cost). Profit-per-WO is the two nets. Money card: NTE · quote · cost · invoiced · profit · margin.
  • The !! waiting for approval bottleneck is client-side (46 WOs in the sample). The One tracks aging and prompts follow-ups; it cannot eliminate the wait.

Status pipeline

One 19-status pipeline everywhere (no per-list overrides), grouped open · active · done · closed, rolled up into 9 phases for the phase bar: Intake · Assessment · Quote · Approval · Scheduled · In Progress · Parts · Done · Invoiced (Parts conditional; !! canceled/postponed is off-pipeline; archive status invoiced).

5User Journeys

Seven journeys cover the platform end to end. Each is written against the as-is process (§4) and annotated with what the prototype already implements BUILT versus what lands in a later release R1+.

J1 · Intake & acceptance OA · TL · ATL · AM

Trigger: a new WO appears on a client CMMS, in email, or in Seamgo. Outcome: an accepted WO sits in a dispatcher's book, or a decline is recorded.

  1. OA monitors the intake sources and surfaces the new WO (today: manual re-entry into ClickUp — the automation win is inbound adapters, Ecotrak first). R1–R2
  2. TL / ATL / AM decides accept or decline; a decline ends the flow with a reason. R1 structured
  3. OA creates the record — ordered intake form (the numbered 13.–38. fields), client, site, trade, NTE, SLA date. BUILT (record + fields; creation UI is R1)
  4. The WO is routed to an OM's book — assignment, not list-moving. Emergency WOs enter as emergency and start a 2-hour acknowledgment clock. BUILT (obligation rule emergency_ack)

Pain removed: multi-source inbox aggregation; the Teams PDF dual-assignment channel is retired at R1–R2.

J2 · Sourcing & assessment dispatch OM (dispatcher)

Trigger: a WO lands in the OM's book. Outcome: a technician has assessed the site and the OM holds photos + findings.

  1. OM searches the pooled vendor map (trade × location) alongside their own book; gaps are filled from online directories. R1 · S6
  2. OM contacts the tech by SMS/call; the Quo thread (calls, transcripts, AI summaries, MMS photos) attaches to the WO's Messages tab. BUILT (mirrored data; live OpenPhone sync via Quotato integration later)
  3. OM schedules the visit: status → assessment scheduled → assessment ongoing. A schedule-owed clock (2 business hours after approval-type triggers) keeps dispatch honest. BUILT
  4. Tech reports back; before photos and findings land on the WO. BUILT (updates feed + photos)

Exception: jobs approved up front skip straight to fulfilment (J4).

J3 · Quote build → approval → send Senior OM → ATL/TL → OA

Trigger: assessment findings are in; status waiting for quote and a 2-business-day quote-owed clock is running. Outcome: the client's CMMS holds the quote; status !! waiting for approval.

  1. Senior OM opens the Quote Builder (roles below senior_om see the controls locked with a tooltip — never hidden). BUILT
  2. Builds INCURRED (work already performed — context, not billed into the total) and one or more PROPOSED options with narrative and line items (service / labor / part / material; amount = qty × rate × 1.5 if OT, computed never stored). Live rail shows cost, grand total, tax (by state), NTE meter, profit, margin. BUILT
  3. Submit → pending_approval. A 4-business-hour quote-review clock now sits on the ATL. BUILT
  4. ATL/TL audits and either rejects (back to draft, with feedback) or approves & sends → sent. BUILT
  5. OA performs TL Rep: pushes the auto-generated client summary + status to the client's CMMS (only client_visible content). R2 adapter; manual today
  6. Waiting on the client, a 5-business-day approval-followup clock prompts chasing. On-site approvals skip the wait entirely. BUILT
J4 · Parts & fulfilment OM · AP

Trigger: client approval (or approved on-site). Outcome: approved work performed on site.

  1. If materials are needed: please order parts → AP orders (ap will order/ap ordered tags today; structured parts stage at R1) → waiting for parts. R1 · S7+
  2. OM redispatches — same tech preferred: job scheduled → job ongoing. BUILT (status flow)
  3. Extra visits when needed (return trip needed) — the exception, not the shape.
J5 · Final soft close & technician payment OM · AP

Trigger: work completed on site. Outcome: WO documentation complete; the tech's payable is settled.

  1. OM uploads after photos and completes the soft-close checklist. BUILT
  2. OM (or AP) raises a payment request: payee = vendor record or manual name+phone, purpose, amount (hardened parsing), method (Zelle, ACH, check, company card, Cash App), optional alternate recipient; prior payments on the WO are shown to prevent doubles. BUILT
  3. The request moves requested → approved → paid in the AP queue (the control point — creation is deliberately ungated); a 2-business-day payment-processing clock sits on AP. BUILT (model + clock; AP queue UI at R1)
  4. Status → done/incurred; the WO's cost side is now real, so profit-per-WO is real.

Why it matters: paying techs fast and reliably is a vendor-retention lever — good techs go where they get paid.

J6 · AR audit → invoice → collection HAR · Senior AR · AR

Trigger: WO reaches final soft close. Outcome: cash collected; WO archived invoiced.

  1. The WO enters the Receivables Audit queue. Grey-Flag rules (ported from Argus) check the record automatically: check-in/check-out present, client quote attached, SharePoint deliverables, CO# format, Admin/Quote release gate. BUILT
  2. AR reviewer clears flags or bounces the WO back to the dispatcher to fix. Trust tiers decide who may release. R1 RBAC
  3. Clean WOs move to Invoicing: Ready → Sent (entered into the client's CMMS) → Paid. BUILT
  4. Collections works << invoiced not paid >> with calls and follow-ups until payment; aging feeds the KPI row and (R2) a collections queue with promise-to-pay. R2
J7 · Pulse triage — obligations Every role, daily

Trigger: continuous — the obligation engine derives clocks from WO/quote/payment state (no cron; a debounced evaluator runs on reads and after relevant writes). Outcome: nothing owed goes silent.

  1. User opens Pulse: Needs me now (tier 2 breached / tier 3 critical) · Due soon (tier 1, ≥80% of clock) · Watching (tier 0 ambient). BUILT
  2. Clocks respect business hours (Mon–Fri 08:00–18:00 CT, paused outside) except emergencies, which run 24×7. Each obligation pings once per tier — ever. BUILT
  3. The user either resolves by evidence — do the owed thing (send the quote, schedule the job, pay the tech) and the obligation clears itself — or snoozes with a mandatory reason, max 72h. There is deliberately no dismiss. BUILT
  4. The bell inbox mirrors pings; read/read-all supported. BUILT

V1 rules (config-as-data): emergency_ack 2h 24×7 · quote_owed 2 bus. days · schedule_owed 2 bus. hours · approval_followup 5 bus. days · quote_review_owed 4 bus. hours (ATL) · payment_processing 2 bus. days (AP) · sla_blown on SLA date passed.

Decided requirements worth restating

  • Quotes: options are internal (client is not choosing between them); OT multiplies rate ×1.5; sales tax derives from state; the client Summary is auto-generated but text-editable. Build = Senior OM+; approve & send = ATL+.

8.2 · Ground truth & precedence

  • When documents conflict, platform-brainstorm/platform-build-plan-handoff.md governs — its §0 realignment supersedes everything below it and defines the precedence order between documents.
  • Process truth: product/wo-lifecycle.md (v3). Parity with it comes before improving on it.

8.3 · Engineering standards (as practiced — now policy)

  • TypeScript ESM everywhere; tsx runs server code directly — no build step until deployment demands one.
  • Zod validation at every API boundary; the single error envelope; role gates return 403 and the UI renders the identical gate as a locked control with a tooltip — never hidden.
  • @theone/shared stays types-only; the web app never imports the DB runtime.
  • Migrations: raw SQL, numbered, append-only. Seeds: idempotent (truncate-and-reload). Demo states are computed with real business-time arithmetic so they land on exact obligation tiers.
  • Derived money is computed, never stored (qty × rate × OT). Status groups are the one sanctioned denormalisation.
  • Every write is attributed in activity_log — humans and service accounts alike.
  • Plain CSS design tokens; the UI Essentials/ brand kit is authoritative (Seamless blue #35b8f3, navy #0a1628, Barlow). The HTML mockups are layout references only.
  • Don't bake "The One" into identifiers — the name is a placeholder.

8.4 · Version control (tightened — current practice is the gap)

Today the entire repo is one commit, with Sprint 5 sitting uncommitted, in a OneDrive-synced folder with no remote. One sync conflict or bad edit and there is no restore point. The three changes below cost minutes and remove the whole risk class.
  1. Commit at least per sprint — message pattern S<n>: <scope> — <exit criterion met>. Commit the current S5 work now.
  2. Add a private remote (GitHub) and push after every commit. Git inside OneDrive is a known corruption/conflict hazard; the remote is the real backup. (Optionally move the working copy out of OneDrive and let GitHub be the sync.)
  3. Tag release gates (r0-prototype, r1-pilot, …). Branch per sprint (sprint/s6-vendors) once more than one person or agent commits; PRs become mandatory at that same moment.
  4. Never commit secrets. .env stays ignored; audit before the first push (see §11 — a sibling repo has live credentials tracked in git).

8.6 · House rules (non-negotiable)

  • ClickUp is READ-ONLY, forever, from every project. GET only — no writes to the live workspace under any circumstances.
  • The client_visible boundary is schema-critical. Nothing reaches a client surface without it; the Quo channel is never client-facing by construction.
  • Obligations have no dismiss. Evidence resolves them; snoozing requires a reason. Do not add a dismiss endpoint "temporarily".
  • Parity before improvement. Every lifecycle stage in §4 must work at parity before the stage is redesigned.

9QA, Acceptance & Release Gates

Per-sprint quality bar

  1. Acceptance checklist — written in the spec before build, executed top-to-bottom against seeded data before the sprint demo. A sprint without a fully checked list does not close.
  2. Scripted UAT on hero WO-39403 — the seeded 7-Eleven refrigeration WO walks all 15 stages (the S4 demo script). New features must appear in that walk wherever the lifecycle touches them.
  3. Role-gate tests — exercise both sides of every gate (e.g. an om actor must see locked controls and receive 403s; senior_om/atl must pass). Seeded personas exist for exactly this.
  4. Deterministic demo states — seed anchors are computed with the real business-time arithmetic so obligation tiers land exactly; keep them that way (no hand-set timestamps).
  5. Self-tests — pure logic (business-time, money math, audit rules) carries its own test file, runnable via tsx. Grow this set with every rule added.
  6. Migration + seed drill — from an empty database: migrate → seed → smoke (health, WO list, WO detail, quote, pulse). Also verify migrate-without-seed (endpoints must degrade gracefully, as the obligation routes already do).
  7. UX audit rules (§6) apply to every new screen: labels, required markers, disabled styling, contrast, locked-not-hidden, tabular numerals.
