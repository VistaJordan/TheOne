Yoda's quoting & technician-payment behaviour, embedded in The One

Yoda is a standalone tool: you reach it through a link ClickUp writes into a custom field, it looks the work order up by TaskId, and it talks back to ClickUp and Teams. In The One the work order is the page — the quote and the payments hang off the WO, and the WO status decides what is allowed. Everything below is live in the code; this page simulates it so the behaviour can be read without running the stack.

Yoda (standalone)

  1. ClickUp webhook → POST /Quote/GenerateQuoteLink writes a URL into the ClientQuote field.
  2. Dispatcher opens /quote?customTaskId=…; prefilled WO fields are read-only.
  3. Builds QuoteSection → QuoteOption → QuoteLineItem; Submit writes the summary into ClickUp; SubmitOnSite also posts Summary + Cost to Teams.
  4. Admin Approval on one option: IsAdminApproved=1, lines IsIncurred=1, section IsLocked=1, siblings soft-deleted, Teams ✅, ClickUp comment.
  5. Payments: /payment?customTaskId=…; create posts to the company's Teams chat; AP Verify adds the amount to ClickUp Cost; delete is soft, with IsPending for processed rows.

The One (embedded)

  1. WO detail → Client quote card “Create quote” / Payables tab “Request payment”. Locked with the reason when the WO status closes them.
  2. Quote builder at /work-orders/:wo/quote; WO context read-only; autosave; permission gates visible-but-locked.
  3. Rounds replace Yoda sections; options carry the Yoda flags; each option priced (incurred + option) × (1 + tax%).
  4. Internal approve/send → client decision on one option (same side effects as Yoda), or decline; Add additional quote opens the next round with the approved work as incurred.
  5. Payments: vendor typeahead, method-specific payout, live W9 alert; the Payments tab at /payments is the queue (lanes, filters, row actions); Pay rolls into 34. Cost; delete semantics identical. ClickUp/Teams posts become outbox rows.

Integrations — what Yoda talks to, and whether The One needs it

Yoda's value is partly in what it pushes outward. For each integration: what Yoda does, what The One does today (the seam), whether we actually need it, and when.

How the outbox seam works

apps/api/src/services/outbox.ts · migration 0004

Every event Yoda would push is written inside the same database transaction as the business change — so the record that “a push is owed” can never drift from the quote or payment it belongs to. Nothing leaves the process yet. When the S6 adapters land they drain status='pending' rows; until then the feature is complete offline and the text that would have been posted is already stored (payment_request.posted_message_plain).

Method lifecycle rules carried over

  • Convert method — Yoda only had PUT Payment/ConvertToAch/{id}. The One generalises it to POST /payment-requests/:pid/convert-method {method} (AP), any code → any code, logged in activity_log.
  • Credit is excluded from W9 — GetReciepientTotal and SetNeedsW9ForTechnicianAsync skip credit; The One's recomputeNeedsW9 and /vendors/:vid/ytd use method <> 'credit' AND recipient_name IS NULL, threshold W9_THRESHOLD = 599.
  • Per-company totals — Yoda split Credit / NonCredit per company (AF, RF, BKR, SFM, TPM) on the technician card; The One keys the same split on billing_entity.
  • Edit locked after processing — Yoda Verify blocks Update; The One's PATCH is only accepted while status='requested'.
  • Alternate payee — Yoda Recipient (store or person) → inline recipient_name / recipient_phone / recipient_is_store; such rows never count toward the technician's W9 total.

Invoicing hooks (what the WO sees)

  • Cost roll-up — Yoda UpdateCostInClickUp on Verify. The One: pay adds the amount to task.fields['34. Cost']; confirm-delete on a paid row subtracts it. Same field ClickUp used for invoicing margin.
  • Quote → money.quote — once the quote is approved | sent | client_approved, getBindableQuoteTotal exposes it on the WO's Money card as the billable figure.
  • Status gating — !! ready to invoice / done/incurred close quote editing but still accept the client decision and payment requests; << invoiced not paid >> / invoiced close both; payment.process (AP) is never gated.
  • Sales tax — stored as a sales_tax_pct on the quote (Yoda: % by ZIP, only when LaborRate.IsSalesTaxRequired), so the future QBO invoice gets the exact rate used on the quote.
  • Not brought — Yoda's QuickBooks SendInvoice / Bfi (AR). Quote retains every input (lines, day, tax %, bill_to); it lands with the Invoicing module via an AccountingAdapter seam.
